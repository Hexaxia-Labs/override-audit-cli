# Plan 6.5: pnpm parent>child correctness + detector polish

**Status:** Pending
**Branch:** `merge`
**Estimated:** half-day
**Date:** 2026-06-08

## Objective

Close the correctness and robustness issues that would surface immediately when an OWASP reviewer runs cve-lite against a real pnpm project, before the Phase 2 handoff. Three clusters, chosen from the backlog:

- **#14 + #15** - pnpm `parent>child` override keys are mishandled (the real blocker)
- **#32** - detector `runnableCommand` emits a `--target` flag the CLI does not parse
- **#16** - `readLockfileNames` silently swallows lockfile parser errors

Deferred to Phase 2 / post-merge: #19 (README), #20 (CHANGELOG), #21 (action.yml), #23 (API reference doc).

## Tasks

### Task 1: #32 - drop `--target` from runnableCommand

Six detectors emit `cve-lite overrides --fix --rule OA00X --target <name>`, but `--target` is not parsed by `src/cli/args.ts`. Drop the `--target ...` portion so the recommended command is `cve-lite overrides --fix --rule OA00X`, matching the migrated docs and the actual CLI surface. Files: oa001, oa002, oa004, oa005, oa006, oa007 detectors. The `shellQuote` import becomes unused in some - remove if so. Closes #32.

### Task 2: #16 - surface lockfile parser errors

`src/overrides/context-builder.ts` `readLockfileNames` returns an empty `Set` on any parser exception, which makes OA001 silently pre-skip with no diagnostic. Change it to push a `skippedDetectors` note (or equivalent diagnostic on the context) when the parser throws, distinguishing "no lockfile" from "lockfile failed to parse." Do not change the happy path. Closes #16.

### Task 3: #14 + #15 - pnpm parent>child partition

**Root cause:** `bareName()` in `src/overrides/parsing/package-json.ts` strips at the first `@`, so `eslint-plugin-ghost>@typescript-eslint/eslint-plugin` becomes `eslint-plugin-ghost>`. OA001 then checks that composite against the lockfile, does not find it, and false-positives as orphaned. OA005 ignores flat-string `parent>child` keys entirely (it only handles object-valued npm nesting).

**Design (the responsibility partition from #15):**

1. **Parsing**: represent `parent>child` keys with their parts. Add fields to the override entry so a detector can see `parent` and the real child target. Keep the existing `packageName` behavior for non-`>` keys unchanged. For `parent>child[@spec]` keys, the child (after `>`, with any `@spec` stripped) is the real target; the parent is the scope.

2. **OA001**: skip entries that are pnpm `parent>child` keys. They are not simple orphan candidates; OA005 owns them. This removes the 4 Ghost false positives.

3. **OA005**: recognize flat-string `parent>child` keys as nested overrides and evaluate them with the existing sub-rule logic (parent in tree? child declared by parent? leaky? flattenable?). The object-valued npm form keeps working.

**Baseline ripple:** Ghost currently asserts 5 findings (4 OA001 + 1 OA002) across several sanity tests. After the fix the count changes (OA001 drops the 4 parent>child false positives; OA005 may add some, depending on whether Ghost's nested overrides are effective). Determine the new Ghost count empirically and update every sanity assertion that encodes it: grep `toBe(5)` / `length).toBe` near Ghost, plus `plan-3-pipeline.test.ts` (the superset/equivalence test where #14 was discovered) and `plan-4.5-detector-polish.test.ts` (Ghost=5). The port-equivalence superset assertion should tighten now that the false positives are gone.

Closes #14 and #15.

## Acceptance criteria

- `npm test` green at the new total (baseline shifts as Ghost count changes; net test count may rise with new parent>child unit tests).

- A corrupt pnpm-lock surfaces a skippedDetectors diagnostic rather than an empty silent skip.
