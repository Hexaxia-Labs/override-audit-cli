# Plan 3.5: Yarn and bun support for the overrides subsystem

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Extend the override-audit subsystem to extract yarn `resolutions` and recognise yarn.lock / bun.lock for lockfile-package-name lookups. After this plan, the 8 OA detectors produce meaningful findings on yarn and bun projects in addition to npm and pnpm.

**Architecture:** Three points of integration:

1. `extractOverrideEntries` in `src/overrides/parsing/package-json.ts` reads `pkgJson.resolutions` and produces entries with `container: "resolutions"`.
2. `readLockfileNames` in `src/overrides/context-builder.ts` calls cve-lite's `loadFromYarnLock` and `loadFromBunLock` when the detected package manager is yarn or bun.
3. OA003 wrong-section generalises from a 2-case check (npm vs pnpm) to a 4-case check (npm / pnpm / yarn / bun) using a `expectedContainer(pm)` table.

**Yarn Berry PnP (no `node_modules`) is explicitly out of scope.** Detectors that need `node_modules` (OA004, OA006, OA008) pre-skip per existing context-builder logic. Yarn classic with `node_modules` gets full coverage. Bun is treated as npm-compatible (it uses the `overrides` field).

**Tech Stack:** TypeScript, Jest. No new runtime deps. Uses existing cve-lite yarn / bun parsers.

**Spec reference:** `docs/merge/2026-05-28-cve-lite-merge-design.md` (parser-coverage section). Closes issue #9.

**Prerequisite:** Plan 3 complete. `audit()`, `verify()`, `applyFix()` available.

### Step 4: Extend `readLockfileNames` in `src/overrides/context-builder.ts`

Find the existing `readLockfileNames` function (added in Plan 2 Task 4). It already has npm + pnpm branches. Add yarn + bun:

```ts
import { loadFromYarnLock } from "../parsers/yarn-lock.js";
import { loadFromBunLock } from "../parsers/bun-lock.js";

function readLockfileNames(projectPath: string, pm: PackageManager): Set<string> {
  try {
    if (pm === "pnpm") {
      const path = join(projectPath, "pnpm-lock.yaml");
      const refs = loadFromPnpmLock(path, false);
      return new Set(refs.map((r) => r.name));
    }
    if (pm === "npm") {
      const path = join(projectPath, "package-lock.json");
      const refs = loadFromPackageLock(path, false);
      return new Set(refs.map((r) => r.name));
    }
    if (pm === "yarn") {
      const path = join(projectPath, "yarn.lock");
      const refs = loadFromYarnLock(path, false);
      return new Set(refs.map((r) => r.name));
    }
    if (pm === "bun") {
      const path = join(projectPath, "bun.lock");
      const refs = loadFromBunLock(path, false);
      return new Set(refs.map((r) => r.name));
    }
    return new Set();
  } catch {
    return new Set();
  }
}
```

**If the cve-lite parser signatures differ from `loadFromPackageLock`-style** (e.g., they require a graph build), adapt. Document any deviation as a concern in the commit message.

### Step 3: Generalise the detector

Replace the existing `misplaced` check with an `expectedContainer(pm)` table-based check in `src/overrides/detectors/oa003-wrong-section.ts`:

```ts
const EXPECTED_CONTAINER: Record<string, OverrideEntry["container"]> = {
  npm: "overrides",
  pnpm: "pnpm.overrides",
  yarn: "resolutions",
  bun: "overrides",
};

const EXPECTED_PATH_PREFIX: Record<string, string[]> = {
  npm: ["overrides"],
  pnpm: ["pnpm", "overrides"],
  yarn: ["resolutions"],
  bun: ["overrides"],
};

export function detect(ctx: OverrideContext): OverrideFinding[] {
  const expected = EXPECTED_CONTAINER[ctx.packageManager];
  const expectedPath = EXPECTED_PATH_PREFIX[ctx.packageManager];
  if (!expected || !expectedPath) return [];

  const findings: OverrideFinding[] = [];
  for (const entry of ctx.overrideEntries) {
    if (entry.container === expected) continue;

    const destination = [...expectedPath, entry.key];

    findings.push({
      ruleId: "OA003",
      severity: "high",
      package: { name: entry.packageName },
      location: { file: "package.json", jsonPath: jsonPointer(entry.path) },
      message: "Override declared in wrong package-manager section",
      details:
        `Project uses ${ctx.packageManager}, but override "${entry.key}" lives in ${entry.container}. ` +
        `${ctx.packageManager} silently ignores this section - the override has no effect.`,
      fix: {
        type: "rfc6902",
        patch: [{
          op: "move",
          from: jsonPointer(entry.path),
          path: jsonPointer(destination),
        }],
        runnableCommand: `cve-lite overrides --fix --rule OA003`,
      },
      references: [
        "https://github.com/OWASP/cve-lite-cli/blob/main/docs/rules/OA003.md",
      ],
    });
  }
  return findings;
}
```

Removes the old npm-vs-pnpm-only conditional. The table is the source of truth.

## Out of scope (documented)

- **Yarn Berry PnP (no `node_modules`).** Detectors OA004, OA006, OA008 pre-skip in this mode. Acceptable; matches existing behavior for npm projects without `node_modules`.
- **Yarn glob syntax for resolution keys** (e.g., `**/lodash`). OA002 only checks the value, not the key, so no immediate false positives. If glob keys produce surprising OA001 behavior on real projects, file a follow-up.
- **OA005 sub-rules tuned for yarn.** Yarn doesn't use pnpm's `parent>child` syntax. Nested object form (`"foo": { "bar": "x" }`) still falls under OA005's existing logic.

## Ready for Plan 4

After Plan 3.5 the override-audit subsystem covers npm, pnpm, yarn (classic + node_modules), and bun. Plan 4 (`cve-lite overrides` CLI subcommand and `--fix` verify hook) consumes the registry without caring about which package manager is in use.
